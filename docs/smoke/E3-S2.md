# Smoke test: lock, logout and startup checks (OPA-41)

Proves that locking and logging out each empty the in-memory metadata cache, and that an outdated `pass-cli` shows as `too_old` right after the shell starts.

These steps act on your real Proton Pass session. `logout` signs `pass-cli` out for everything that uses it, so you have to sign in again.

## Prerequisites

1. From a checkout of the branch under test, install that checkout: `omarchy plugin add "$PWD" --enable`. If the plugin is already installed, `make dev` copies the checkout over it instead.
2. Restart the shell: `omarchy restart shell`.
3. A signed-in `pass-cli` 2.7.1 or newer, with at least one vault that has items.
4. For the lock steps, a session lock code: `pass-cli session create-lock`.

Status command used below: `omarchy-shell omapass cacheInfo`. It prints counts and the state only.

## too_old at startup

This uses a temporary `pass-cli` wrapper that reports an old version and passes every other command to the real one.

1. Print the shell's `PATH`, one directory per line: `tr '\0' '\n' < /proc/"$(pgrep -f 'quickshell.*omarchy' | head -1)"/environ | grep '^PATH=' | cut -d= -f2- | tr ':' '\n'`. Pick a directory you can write to that is listed before the one holding the real `pass-cli` (`command -v pass-cli`), and make sure it has no `pass-cli` of its own.
2. Create `pass-cli` in that directory, with the real path in the last line, then `chmod +x` it:

   ```sh
   #!/bin/sh
   if [ "$1" = --version ]; then echo "Proton Pass CLI 2.7.0 (0000000)"; exit 0; fi
   exec /usr/bin/pass-cli "$@"
   ```

3. Run `omarchy restart shell`, wait a few seconds without opening the overlay, then run `omarchy-shell omapass cacheInfo`. Expected: `state` is "too_old" and `items` is 0.
4. Delete the wrapper, then run `omarchy restart shell`. Open the overlay (`omarchy-shell omapass open`), wait a few seconds and run `cacheInfo`. Expected: `state` is "ready" and `items` is greater than 0. Close the overlay (`omarchy-shell omapass close`).

## lock

1. With the cache loaded (`state` "ready", `items` greater than 0), run `omarchy-shell omapass lock`, then run `cacheInfo`. Expected: `items` and `vaults` are 0 at once.
2. After a few seconds run `cacheInfo` again. Expected: `state` is "locked" and `items` is 0.
3. Open the overlay, wait a few seconds and run `cacheInfo`. Expected: `state` is still "locked" and `items` is 0. Close the overlay.
4. Unlock in a terminal: `pass-cli session unlock`. Run `omarchy-shell omapass refresh`, wait for `refreshing` to be false and run `cacheInfo`. Expected: `state` is "ready" and `items` is back.

Without a session lock code, `lock` cannot succeed: the cache still empties at once, then fills again.

## logout

1. With the cache loaded, run `omarchy-shell omapass logout`, then run `cacheInfo`. Expected: `items` and `vaults` are 0 at once.
2. After a few seconds run `cacheInfo` again. Expected: `state` is "signed_out" and `items` is 0.
3. Open the overlay, wait a few seconds and run `cacheInfo`. Expected: `state` is still "signed_out" and `items` is 0. Close the overlay.
4. Sign in again in a terminal: `pass-cli login`. Run `omarchy-shell omapass refresh`, wait for `refreshing` to be false and run `cacheInfo`. Expected: `state` is "ready" and `items` is back.

## logs

1. Check the logs: `journalctl --user -b -t omarchy-shell --since "-10 min" | grep -i -E "omapass|qml|warn|error"`. Expected: no QML errors or warnings that name this plugin's files.

## Remove afterwards

1. If you created a lock code only for this test: `pass-cli session remove-lock`.
2. `make uninstall` (runs `omarchy plugin remove elvisgastelum.omapass`). Expected: the plugin is removed.
3. `omarchy restart shell`.
